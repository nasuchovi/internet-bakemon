# ヒロイン自動生成システム 設計メモ

> プレイヤーが容姿・声質・性格を設定し、その通りにAIがヒロインを生成する仕組み。
> 実装のプロトタイプは [`/heroine-lab`](../heroine-lab/) にある。

## 結論

**技術的には作れる。** 難所は生成技術そのものではなく、次の3点。

1. **一貫性** — 毎回違う顔が出てくると「自分が作ったヒロイン」にならない
2. **コストとレイテンシ** — 誰が・いつGPUを回すか
3. **規約と法** — R18であるがゆえに、使えるAPI・配布先・決済手段が絞られる

順に書く。

---

## 1. 全体構成

```
  プレイヤー設定 (容姿 / 声質 / 性格)
        │
        ▼
  ┌──────────────┐
  │  schema.js   │  設定項目の唯一の定義（UI もここから自動生成）
  └──────┬───────┘
        ▼
  ┌──────────────┐
  │  safety.js   │  ★必須通過点：成人限定・実在人物遮断・禁止語検査
  └──────┬───────┘
        ▼
  ┌──────────────┐
  │  compile.js  │  設定 → 各エンジンの入力へ変換
  └──┬────┬───┬──┘
     │    │   └────────────┐
     ▼    ▼                ▼
 画像prompt  音声params   ペルソナ文
  + seed      (正規化)     (LLM system prompt)
     │          │             │
     ▼          ▼             ▼
 ┌────────┐ ┌────────┐  ┌──────────┐
 │ComfyUI │ │ SBV2   │  │ローカルLLM│   ← adapters/ で差し替え可能
 │ A1111  │ │VOICEVOX│  │(OpenAI互換)│
 └────────┘ └────────┘  └──────────┘
```

差し替え可能にしてあるのが要点。生成エンジンは1〜2年で陳腐化するので、
ゲーム側のロジックがエンジンのAPIに直接触らない構造にしておく。

## 2. 一貫性をどう作るか

「同じヒロインが毎回出てくる」を成立させる手段は、弱い順に4段。

| 手段 | 一貫性 | コスト | 備考 |
|---|---|---|---|
| **seed固定 + タグ固定** | △ | ゼロ | プロトタイプの既定。構図が変わると顔も揺れる |
| **IPAdapter / reference画像** | ○ | 低 | 最初の1枚を「正」として以降を寄せる |
| **キャラクターLoRAの都度学習** | ◎ | 高 | キャラクリ時に数分〜。ローカル配布だと現実的でない |
| **パーツ合成（Live2D / 差分レイヤ）** | ◎ | 中 | AIは各パーツ生成に使い、組み立ては従来手法 |

本プロトタイプは第1段を実装済み。`compile.js` の `deriveSeed()` は
**容姿に関わる項目だけ**からseedを導出する。声や性格のスライダーを動かしても
顔が変わらないので、プレイヤーが安心して触れる。

```js
const IDENTITY_FIELDS = ['name','ageBand','hairLength',...];  // ← これらだけがseedに効く
```

実運用では第2段（IPAdapter）まで上げるのが費用対効果が良い。
キャラクリ確定時に基準画像を1枚生成 → 以降のシーン画像はそれを参照して生成する。

## 3. いつ生成するか

**全部リアルタイム生成は破綻する。** 現実的な配分はこう。

| タイミング | 生成するもの | 待ち時間の許容 |
|---|---|---|
| キャラクリ確定時（1回） | 基準立ち絵、表情差分5〜10枚、衣装差分 | 数分（演出でごまかせる） |
| シーン遷移時 | シーン画像（任意・スキップ可） | 10〜30秒 |
| 台詞ごと | 音声（TTS） | 1秒未満（要ローカルTTS） |
| 台詞ごと | テキスト（LLM） | ストリーミングで体感を消す |

画像は「キャラクリ時に一括、以降は差分だけ」。音声とテキストは常時リアルタイム。
この配分ならローカル実行でも成立する。

## 4. どこでGPUを回すか

| 方式 | 長所 | 短所 |
|---|---|---|
| **プレイヤーのPC（ローカル）** | 運営コストゼロ、規約の縛りが最小 | VRAM 8GB以上を要求。導入で脱落する |
| **自前サーバ** | 動作環境が揃う | GPU代が売上に直撃。キャラクリ1回あたりの原価を先に計算すること |
| **商用API** | 楽 | **成人向け出力は各社の利用規約で禁止されているのが通例**。実質使えない |

R18作品では商用API（OpenAI・Anthropic・Google等の画像/テキスト生成）は
**規約上そもそも選択肢に入らない**。この制約が構成の大半を決める。
プロトタイプの既定がローカルサーバ向けアダプタなのはそのため。

現実的な着地点は「ローカル実行を基本 + 非力な環境向けにプリレンダ済み素材で代替」。

## 5. 規約・法務チェックリスト

技術以上に事前確認が要る項目。**着手前に潰しておくこと。**

- [ ] **画像モデルのライセンス** — 生成物の商用利用可否。SDXL派生モデルは
      マージ元によってライセンスが異なり、商用不可のものが混ざっていることがある
- [ ] **音声ライブラリの規約** — VOICEVOXは「エンジン」と「キャラクター」で規約が別。
      多くのキャラクターは成人向け用途を明示的に禁止している。
      Style-Bert-VITS2などで自前音声を使う場合も、学習元話者の許諾が要る
- [ ] **声優・話者の許諾** — 実在話者の声を学習させる場合は用途を明記した契約が必須
- [ ] **配布プラットフォームの規約** — DLsite / FANZA / Steam / itch.io で
      AI生成物の扱いが異なる。「AI利用の申告義務」「AI作品の販売区分」を確認
- [ ] **決済事業者の規約** — クレジットカードブランドの成人向けコンテンツ規制。
      プラットフォーム経由の販売なら実質ここは委譲できる
- [ ] **年齢確認** — 配布形態に応じた実装。プロトタイプは自己申告ゲート止まり
- [ ] **わいせつ物頒布（刑法175条）** — 日本国内向け配布では修正処理が必要
- [ ] **児童ポルノ禁止法** — 生成物であっても実写的表現は極めて危険。
      本システムが年齢層を成人のみに固定し、negative promptを強制注入しているのはこの線を守るため
- [ ] **肖像権・パブリシティ権** — 実在人物の再現をユーザーに作らせない。
      自由入力欄のブロックリストは最低限の防波堤

### 実装済みの安全策

`safety.js` はパイプラインの必須通過点として実装してある。

- 年齢層の選択肢は成人のみ。カード読込時も再検査する
- `ALWAYS_NEGATIVE` を negative prompt へ常時注入（UIから外せない）
- 自由入力欄を語彙検査。違反時はアダプタを呼ばずに拒否
- `blocklist.local.json` を置けば禁止語彙を追加できる（配布先の禁止語彙・実在人物名）

R18表現そのものの語彙は**リポジトリに同梱していない**。
`ratings.local.json` を置くと `compile.js` が読み込んでプロンプト末尾に差し込む、
という差込口だけを用意してある。

## 6. 推奨スタック（2026年時点の一例）

| 役割 | 選択肢 |
|---|---|
| 画像 | ComfyUI + SDXL系イラストモデル（ライセンス要確認）+ IPAdapter |
| 音声 | Style-Bert-VITS2（自前学習の話者） |
| 台詞 | ローカルLLM（Ollama / llama.cpp、14B前後が対話の質と速度の折衷点） |
| ゲーム基盤 | Godot / Unity / Web（本プロトタイプは素のHTML+ESM） |

## 7. 現状のプロトタイプでできること

`/heroine-lab/index.html` をブラウザで開くと（バックエンド不要）:

- 27項目の設定UI（`schema.js` から自動生成。項目追加は1行）
- 設定 → 画像プロンプト / 音声パラメータ / ペルソナ文 へのリアルタイム変換
- モックアダプタによる立ち絵プレビュー・読み上げ・会話（配線確認用）
- 禁止語の即時ブロック
- キャラカード（JSON）の書き出し／読み込み、localStorageへの自動保存
- ComfyUI / A1111 / Style-Bert-VITS2 / VOICEVOX / OpenAI互換LLM への接続設定

## 8. 次にやること

1. IPAdapterによる一貫性強化（基準画像→シーン画像）
2. 表情差分の一括生成（キャラクリ確定時にまとめて焼く）
3. 生成キューとキャッシュ（同一seed+同一promptの再生成を避ける）
4. 実際のゲーム進行（シナリオ・好感度）との接続
5. 配布形態の決定 → それに応じた年齢確認・修正処理の実装
